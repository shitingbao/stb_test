## 4. 不符合 / 高风险待验证（与代码审查强相关）

### 4.0 标注为「不符合」的用例（**有条件**：仅当还款入账走 `wallet_recharge.go` 银行卡拆分逻辑时）

以下用例的预期依赖「每笔账单分摊金额不超过该账单待还；溢出单独进可用额度/现金钱包」。静态代码下，**银行卡路径**存在将 **大于最后一笔 `PendingAmount`** 的金额仍记在该账单上的逻辑，进而 `WalletBillAmountChange` 可能把 `pending_amount` 减成负数，**与用例预期不一致**。

| 用例 ID | 用例名称（节选） | 判定 |
|---------|------------------|------|
| **TC-414** | FIFO规则-还款后有溢出入现金钱包 | **不符合**（若实际走银行卡入账循环且存在多笔待还、还款额在还清倒数第二笔后仍有结余） |
| **TC-412、TC-413、TC-437、TC-439** | FIFO 相关 | **待验证**：若全程走 `payRechargeVersion2` + `GetPendingBillsByWalletId`（`BillDate` 升序），与 FIFO 一致；若部分流量走银行卡路径，需按上款与用例数据复算 |

> 说明：此处「不符合」是**代码路径与用例数据组合下的静态推断**，仍需用同一入金渠道做集成测试确认生产行为。

### 4.1 还款 FIFO 与「最后一笔账单」逻辑（**高风险 · 待验证**，可能影响 M8 多条）

**用例示例**：TC-412、TC-413、TC-414、TC-437、TC-439（均要求按账期**由旧到新** FIFO 分摊；溢出进现金/额度等）。

**代码事实**：

1. **MQ Version2 路径**（`payRechargeVersion2`）：待还账单来自 `GetPendingBillsByWalletId`，DAO 为 **`OrderAsc(BillDate)`**，循环按切片顺序抵扣，与「旧到新」一致。文件内注释写「出账时间倒序」与 DAO 升序**不一致**，以 **DAO 排序为准**。
2. **银行卡入账路径**（`wallet_recharge.go` 中 `GetBillsForBank` + 循环）：待还列表第一段为 **`OrderAsc(BillDate)`**，但循环内对 **`i == len(walletBills)-1`** 时将 `amount = leftAmount`，可能使**最后一笔**账单分配金额 **大于** 该笔 `PendingAmount`。随后 `WalletBillAmountChange`（`WalletBillTypeBankRecharge`）对银行卡分支为 **`pendingAmount -= changeAmount`**，**未见**按 `PendingAmount` 上限截断。

**代码依据（节选）**：

### 4.2 其它未裁定为「不符合」的项

- **退款金额等于可退额度**：`WalletRefund` 使用 `if balance < reqAmountInCents` 判不足，**等于时可通过**，与「等于可全额退」一致。
- **返点切换为直接抵扣需余额为 0**：`wallet.go` 有对应错误提示，与 M6 中「余额非 0 拒绝」类用例方向一致。
- **流水明细导出类型 9**：后端 `EXPORT_TASK_TYPE_WALLET_DETAIL = 9` 与前端 `TaskType.WALLET_LIST_EXPORT_BY_TRANSACTION = '9'` **一致**。
